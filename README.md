# nar-collector

地方競馬(NAR)の過去成績・確定オッズ収集と、期待値評価の基盤。

## 設計判断

**過去のオッズは3層に分かれる**

| データ | 過去取得 | 用途 |
|---|---|---|
| 全馬の確定単勝オッズ・人気 | ○ 何年分でも | **EV検証の主データ** |
| 各券種の的中目の払戻 | ○ | 三連系オッズ再構成の較正点 |
| 外れ目のオッズ・時系列推移 | × | 前方収集でのみ入手可 |

→ **単勝・複勝は今日から過去10年のフルバックテストが可能。**
確率モデル本体にオッズは不要(条件と戦績から着順確率を推定するのが仕事)。
オッズが要るのは検証時だけで、運用時はリアルタイムで手に入る。

**控除率の壁**: 単勝が最も低く三連単が最も高い。三連単は市場を4割近く
上回らないと損益分岐しない。データが完全に揃っていて、かつ最も勝ち目のある
券種が同じ場所(=単勝)にある。ここから始めること。

## 使い方

```bash
pip install -r requirements.txt

# 0) 初回のみ: セレクタ校正。実HTMLを1レース取ってCOLMAPを合わせる
python -m nar.calibrate --date 2026-08-01 --baba 44 --race 11

# 1) キューに積む + 収集開始
python -m nar.backfill --since 2023-01-01 --limit 3000 --interval 2.0

# 2) 再開(何度でも安全。done は再取得しない)
python -m nar.backfill --limit 3000

# 3) 進捗
python -m nar.backfill --report
```

## なぜ競艇より遅いのか

**BOAT RACE は番組表(B)・競走成績(K)を1日1ファイルのLZHで一括配布**しており、
1ファイルに全24場×12Rが入っている。365リクエストで1年分が終わる。

**地方競馬にこの一括配布は存在しない。** 1レース＝1ページなので、
同じ1年分で約5万リクエスト。**150〜200倍**。設計の問題ではなく供給側の違い。

対策は2つだけ:

| 施策 | 効果 |
|---|---|
| 開催日カレンダー先読み (`shards calendar`) | 総当たりの404空撃ち7割を除去 → リクエスト1/3 |
| matrix シャード並列 (`--shard i/n`) | 別VM・別IPで n 倍。**上限6** |

### 規模感（並列後）

- 1ジョブ: 2秒間隔 × 5.5h ≒ **9,900R**
- 6シャード ≒ **一晩で約6万R**
- 2〜3年分(10〜15万R) ≒ **3晩**

`rowid % n` で担当を決めるため、各ジョブが空DBから始めても
重複・欠落なく分割される(テスト済み)。

## ⚠ リポジトリは Public にすること

Private の Actions 無料枠は月2,000分。6h × 6ジョブ = 2,160分で**初日に枯れる**。
Public なら無制限。

## ⚠ 並列度6を超えないこと

IPが分かれても、相手側から見れば同一サイトへの合計リクエスト数。
10並列は迷惑だし、ブロックされたらプロジェクトごと終わる。
`--interval` は2.0未満に設定できないようコードで固定してある。

## 最重要: リーク防止

`features.py` の全集計は `shift(1)` で1走ぶん過去にずらしてある。
`assert_no_leak()` を CI に入れること。人間のレビューは必ず失敗する。
**分割は必ず時系列 (`time_split`)。ランダム分割は絶対禁止。**

バックテストで回収率150%が出たら、まず疑うのはリークであって才能ではない。
